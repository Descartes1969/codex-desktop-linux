# From Isolation to Host-Native Full Access: Engineering an Unofficial Codex Desktop Wrapper for Linux

By Descartes1969

There is a large gap between making an Electron window appear on Linux and producing a desktop tool that can be trusted with real development work. A window can open while Chromium's renderer sandbox is disabled. It can display a sign-in page while writing into the wrong profile. It can advertise “Full access” while an outer namespace quietly hides the user's Git configuration, credentials, network and most of the filesystem. It can appear to close while an invisible process keeps the single-instance lock forever.

This project began with an audit of `ilysenko/codex-desktop-linux`, an unofficial community wrapper that converts OpenAI's macOS ChatGPT/Codex desktop payload into a Linux Electron application. The audited baseline was commit `7166d1153fd99647fb080605c8b2a8f22b50b08f`. The goal was not to create an official OpenAI Linux application, and this work does not make that claim. The goal was narrower and more demanding: determine whether the wrapper could become a usable, evidence-qualified Linux desktop on one Ubuntu/GNOME/X11 workstation.

The result required two architectures. The first proved that strong outer isolation was feasible. The second removed that isolation from the Full-access path after it became clear that the containment boundary contradicted the product requirement. That reversal was not an abandonment of security. It was a correction of which component owned which authority.

## Starting from a pinned audit

The initial audit found a capable and fast-moving project, but it also found reasons not to equate successful packaging with acceptable runtime behavior. At the pinned revision, the generated launcher unconditionally included `--no-sandbox` and `--disable-gpu-sandbox`. Normal startup could discover, install or repair a Codex CLI and synchronize bundled plugin material into the user's Codex home. Ordinary builds followed a moving DMG endpoint unless stronger pinning was supplied. Native packages could also add an updater, a user service and a privilege path for package installation.

Those findings defined the first success criteria. The candidate had to run without the Chromium sandbox-disable flags, use a disposable Codex home and Electron profile, use an exact CLI without updating it, and omit updater, plugin synchronization, browser integration, Computer Use, optional features, listeners and services. Inputs and generated bytes had to be identified by hash. A visible window was only one observation among many; process privileges, namespaces, files, sockets and cleanup mattered just as much.

That discipline prevented a common failure mode in compatibility projects: treating the first configuration that draws pixels as the architecture. Here, drawing pixels was the beginning of qualification.

## The first secure architecture

The first serious design put the generated application inside a private Bubblewrap environment. It used private user, PID, mount and network namespaces; a narrow AppArmor profile; isolated persistent state; a dedicated display path; and eventually slirp4netns, a user-space network stack, for outbound networking. The application payload was mounted read-only. A version-matched Chromium SUID helper—a narrowly privileged sandbox bootstrap executable—was supplied with exact ownership and mode. The application ran under mapped credentials with its effective, permitted, inheritable and bounding capability sets cleared. Renderer evidence showed seccomp system-call filtering active and `NoNewPrivs=1` without the sandbox-disable flags.

The private Bubblewrap implementation required an explicit, checked credential transition. UID/GID mapping and privilege-sensitive setup occurred in the verified order; the final application identity had its capabilities cleared before payload execution.

The full Electron qualification used one authenticated Bubblewrap invocation and one application launch. It proved that the private network namespace had only loopback and no route, the host network namespace differed, prohibited devices and broad desktop buses were absent, candidate mounts were read-only, and the Chromium helper had the expected bytes, owner and mode. The renderer retained its own Chromium sandbox. Cleanup restored the host-visible helper/state ownership and left no live sockets, mounts or processes.

Several failures along the way were instructive. The workspace path contained spaces, which broke some upstream Meson test scripts. The application expected an icon as an unpacked file even though the authenticated PNG was present inside its Electron application archive (ASAR), so the runtime supplied exactly that file through a sealed read-only bind. Neither issue justified weakening the security model; each was repaired at the owner of the failed assumption.

Once the private core passed, it was productized. A desktop entry led to one launcher and lock, then a namespace mapper, private Bubblewrap, private namespaces, slirp networking and the real X display. An installed AppArmor policy replaced temporary setup cycles. The launcher kept a dedicated state tree and exposed at most one selected workspace. Slirp disabled host loopback and inbound forwarding. Chromium configuration was copied into a private temporary location and back on normal exit because its singleton-lock behavior did not tolerate the mapped bind topology.

At that stage, the architecture was reasonable. It demonstrated that the unofficial wrapper did not need Chromium's `--no-sandbox` escape hatch. It preserved an authenticated app inside an explicit containment boundary. It provided a controlled environment in which optional functionality could be restored incrementally.

## Restoring desktop functionality

The upstream wrapper contained a growing set of Linux compatibility descriptors: declarative patch definitions with target and validation rules. Twenty-six relevant descriptors covered Computer Use UI and plugin gates, browser integration, updater bridges, feature enablement, navigation and recovery behavior. They were enabled and tested as a group. Four hundred eleven descriptor tests passed, and 25 descriptors either applied or were already present.

The 26th descriptor was deliberately not forced. Its Computer Use settings-availability patch no longer matched the complete current minified/settings contract. Forcing it would have applied an unverified patch to changed bundled application code. The correct action was to reject the stale patch, then retarget and verify the exact current predicate before installation.

Authentication also had to be treated as product state, not a screenshot. Interactive ChatGPT sign-in was left to the operator; credentials, MFA and private browser contents were never automation inputs. Later launches had to reuse the same dedicated Electron profile and still produce a real model response. A custom OAuth BrowserWindow was explored in a build workspace, rejected, and never installed. The production profile instead followed the application's normal sign-in path.

The final feature repair changed only the current settings-availability predicate and guarded it with an explicit Linux Computer Use UI flag. The complete suite then reached 412 passing descriptor/patch tests. The production package included the Linux Computer Use backend, a CLI wrapper that selected it, the plugin and marketplace manifests, and a compatibility implementation of the screenshot command expected by the backend.

Functional qualification went beyond checking that “Computer use” appeared in Settings. The backend started through the MCP integration. Per-action Allow once, Deny and Always allow controls appeared. A screenshot was captured through the bounded compatibility shim. On X11, the tool observed and controlled a dedicated native test window, typed an exact value, clicked it and received that value back. It also targeted a dedicated browser profile instead of wandering through an existing personal browser session.

The isolated architecture intentionally did not expose broad DBus or portal access. That meant semantic AT-SPI accessibility actions were unavailable in the tested configuration; the backend failed closed to coordinate/X11 behavior. This is a limitation, not a hidden success. Linux desktop control crosses compositor, accessibility, input and permission boundaries, so “Computer Use works” must always name the backend and the actions actually tested.

Authentication persistence, Computer Use and a model response were finally proven together. A bounded abnormal-exit fixture also verified that a crash leaving mapped ownership or helper modes behind could be recovered by the next ordinary launch. Recovery selected the exact production ancestry and state; it did not use a broad process-name search or turn manual `chown` into a lifecycle feature.

At this point the isolated desktop was a qualified product for its stated workflow. Then the workflow changed.

## The architectural reversal

The decisive problem appeared when the desktop was asked to perform real host assignments in Codex “Full access” mode. Inside the application, Full access removed the Codex workspace sandbox. Outside it, the wrapper still supplied a private home, private Codex state, mapped identity, workspace-only mounts, private network and `NoNewPrivs=1`.

The consequences were operational, not theoretical. GitHub authentication lived in the wrong place. Git configuration was a sandbox-local proxy rather than the durable host file. Network behavior depended on the temporary slirp layer. Ordinary host paths were absent or read-only. Normal privilege transitions were structurally blocked. An invisible resident application could keep an outer lock even though no useful window remained.

It would have been possible to add bridges: copy GitHub credentials into isolated state, proxy selected host configuration, forward more network destinations, broker privileged operations, add more bind mounts, or maintain a cleanup service. Each exception would have made the boundary harder to explain and easier to get wrong. More importantly, it would have repaired symptoms owned by the outer wrapper while preserving the contradiction.

The repair chosen for this requirement was simpler. Full access became a host execution mode. The desktop entry still invokes one production launcher, but that launcher now directly executes the existing host-native `app/start.sh` as the logged-in user. It inherits the real HOME and XDG developer state, real Git/GitHub/Codex configuration, host process and network namespaces, and ordinary privilege attributes. It explicitly selects the already authenticated Electron profile and retains the Computer Use wrapper.

Removed from this path were outer AppArmor confinement, private Bubblewrap, user/PID/IPC/cgroup/network namespaces, slirp, mapped UID/GID state, the temporary home/config boundary and ownership by the outer lock. No credential synchronizer, GitHub-specific bridge, passwordless-sudo rule, general-purpose setuid helper, privileged daemon, RPC broker, watchdog or periodic killer replaced them.

This does not make the earlier architecture a mistake. It proved that isolation could work and exposed exact Linux behaviors that an unsandboxed launch would have hidden. It was appropriate when the requirement was a tightly bounded desktop. It became inappropriate when the requirement was honest host-level Full access. The trust boundary changed because the product intent changed.

## Security retained after removing the outer sandbox

“Full access” did not mean disabling every sandbox. The final architecture separates two questions.

First, what authority should an intentionally authorized Codex agent have? In the selected mode, it has the logged-in user's host authority, ordinary network and durable developer state. For this qualified workstation, the selected Codex policy was `danger-full-access` with approval prompts disabled. This describes the tested configuration, not a recommended default for other installations. Unix permissions still constrain the account, and sudo remains an explicit host mechanism; the project did not add passwordless sudo.

Second, what should contain a compromised or buggy Electron renderer? Chromium's internal process sandbox remains enabled. The production runtime uses a purpose-built, version-matched SUID helper owned by root with mode 4755. Qualification observed renderer sandboxing enabled. The old AppArmor profile remains installed for legacy helpers but is no longer on the active Full-access launch chain, so it is not credited with protecting the current app.

Those boundaries are complementary, not interchangeable. A renderer sandbox is not a substitute for the agent's workspace/host authorization model. Conversely, intentionally granting the agent host access does not require abandoning Chromium's renderer isolation.

## Linux-specific compatibility work

Retaining Chromium's sandbox exposed an installation-path problem on the qualified build and layout. Direct sandboxed startup failed when the production executable was reached through its path containing spaces.

The repair did not copy or rebuild Electron. A no-space facade contains a hard link to the unchanged production Electron inode and symlinks to its actual libraries and resources. The matching Chromium helper lives at a no-space system path and is selected through `CHROME_DEVEL_SANDBOX`. Hash and inode checks prove that the facade executable is the production executable.

The no-space facade plus matching helper made that observed fixture work. The retained evidence does not isolate whether Chromium's SUID broker, Electron invocation or packaging was the responsible layer. It also does not prove that Electron or Chromium generally cannot run from paths containing spaces, or that other Electron apps require the same facade.

Computer Use had its own path contracts. The app expected a CLI-facing backend and a familiar screenshot program interface; the Linux package supplied immutable wrappers that resolved to the bundled backend and translated screenshot requests into the tested GNOME/X11 command. Again, the wrappers were narrow: they repaired the name and argument contract instead of expanding the desktop boundary.

Lifecycle behavior was equally Linux-specific. Upstream-style close-to-tray behavior interacted badly with the outer supervisor and lock: the visible window disappeared, but the app could remain stranded without a useful presentation path. Synthetic ICCCM window-manager close messages helped with diagnosis but did not prove what a user experiences with GNOME's client-side title bar.

## X should mean X

The final requirement was literal: clicking the title-bar X should terminate the application and permit a normal relaunch.

The implementation changed the Linux managed-window close path. If a window is more than five seconds old, closing it schedules Electron's terminal `app.exit(0)` path. The grace period excludes internal window replacement during startup. There is no background watcher, tray workaround, process-name killer or duplicate launcher.

The qualification report records that the test clicked the actual top-right X with the pointer rather than sending another synthetic close. The archived machine-readable cycle fixtures do not preserve the input event itself; they independently preserve the resulting zero Electron processes, zero visible windows, no namespace mapper/Bubblewrap/slirp remnants, free old and current launcher locks, correct state/helper ownership, and linkage to the next authenticated usable launch.

The report records three consecutive pointer-X cycles without terminal cleanup or manual reset, while the archived cycle and relaunch records independently prove three consecutive teardown/relaunch outcomes using four distinct Electron main processes. File → Quit ChatGPT was tested separately and has its own clean full-stack record.

This sounds obvious—X should mean X—but it captures a broader testing principle. A protocol-level substitute is not the user action when client-side decorations, tray policy, compositor behavior and Electron lifecycle code all participate. Test the exact action whose semantics matter.

## Evidence as part of the implementation

The project repeatedly used hashes, frozen candidates, exact fixtures and fresh review. That discipline caught real errors in the evidence package itself.

An early final review rejected the host-authority candidate even though the implementation looked credible. The required checksum manifest was missing. One changed-production hash record was stale. The X-close fixtures proved teardown but did not link every close to the next usable relaunch. The File → Quit record proved that one PID died but not that the complete stack and locks were clean.

The candidate was frozen again. Checksums covered every changed production/configuration file and the decisive reports. Each X-close record was linked to the next distinct normal launch. File → Quit gained full process, window, lock, ownership and helper checks. A genuinely fresh independent, read-only reviewer verified the hashes against current bytes and accepted all 18 predicates.

That sequence matters because evidence can be stale even when code is correct. A reviewable artifact is not a narrative saying tests passed; it is a frozen identity plus fixtures that prove the actual acceptance conditions.

## Current result

Current production is a GNOME-launchable, unofficial ChatGPT/Codex desktop wrapper. It uses one host-native launch path, the real logged-in identity and durable HOME/XDG/Git/GitHub/Codex state, ordinary host networking, an explicitly retained authenticated Electron profile, retained Linux Computer Use integration and approval UI, Electron single-instance handling, bounded stale-webview recovery, and Chromium's SUID/renderer sandbox.

The tested Codex policy is Full access with approvals disabled. Under the final host-native architecture, model response, host read/write, network, authentication persistence, Computer Use MCP startup/availability, real title-bar close/relaunch and File → Quit passed on the qualified workstation. The deeper screenshot, input, native-app and dedicated-browser Computer Use actions described earlier were qualified under the preceding isolated architecture; the host-authority stage proved that the integration remained available, not that every earlier action was freshly repeated. These results are bounded to the captured versions, desktop environment and actions; they are not performance claims or universal security guarantees.

## Potential upstream value

At `ilysenko/codex-desktop-linux` default-branch HEAD `de575d0` inspected on 2026-08-08, upstream had moved substantially since the pinned audit. That revision bundled Linux Computer Use, contained the then-current settings-card patch and transactional patch-drift handling, revalidated stale Electron processes with pidfds (kernel handles for safely referring to processes), and included bounded Linux quit cleanup ending in `app.exit(0)`. Those revision-specific solutions supersede several local one-off repairs and are the appropriate starting point for rebasing; the repository is fast-moving, so they must be rechecked against any later HEAD.

Two findings may still have portable value. First, at inspected HEAD `de575d0`, `launcher/start.sh.template` constructed Electron arguments containing `--no-sandbox` and `--disable-gpu-sandbox`. The local result proves only that a matching SUID helper retained Chromium renderer sandboxing on the qualified Ubuntu host and build. A useful upstream proposal would need packaging-aware helper provenance, ownership/mode handling, AppArmor/user-namespace analysis and regression tests—not merely deletion of two flags.

That proposal became upstream PR #1264. Repository-owner review found two real
architectural blockers in its first version: successful warm-start IPC could
return before helper and final-argument validation, and Chromium-specific
policy was placed in shared launcher core. The corrected candidate rejects a
sandbox-requested launch whenever an existing primary's Chromium mode cannot
be authoritatively verified. It does so before both warm-start IPC and
Electron's second-instance route, without killing the healthy resident. The
Chromium rules now live in disabled-by-default
`linux-features/chromium-sandbox`; shared core retains only generic feature-hook
controls.

Real Electron 42 qualification exposed one further portability constraint.
Chromium preferred the generated sibling `chrome-sandbox` over
`CHROME_DEVEL_SANDBOX`, so the feature now preserves the generated helper as a
byte-reference while leaving the sibling path absent. It supports a
user-owned, user-managed generated Electron app and rejects native package
creation, where installed Electron ownership prevents that environment
fallback. This maintainer-driven correction refines the portable upstream
architecture without rewriting the earlier host-qualified historical result.

Second, the exact local five-second mature-window heuristic is **NEEDS_REBASE_OR_RESEARCH**, not a ready-made upstream fix. It passed bounded qualification on one Ubuntu/GNOME/X11 workstation, while inspected upstream HEAD `de575d0` had its own tray, warm-start, single-instance and quit-cleanup architecture. The portable value is the user-visible requirement and the test predicates: click the actual client-side title-bar X rather than a synthetic ICCCM substitute; verify zero stale processes and locks; then verify that the following ordinary launch is authenticated and usable. Any upstream implementation should be designed against the then-current upstream lifecycle rather than copied from the local ASAR patch.

Other work is clearly local. The no-space facade responds to a specific installed path. The authenticated profile and host credential state belong to one machine. The private Bubblewrap topology is valuable research or an optional restricted mode, but it should never be presented as Full access.

## Lessons

The project produced a few durable engineering rules.

Repair the owner of the failure. An icon-path mismatch needs an exact icon bind, not a weaker filesystem. A stale process needs identity validation, not a broad `pkill`. A contradictory outer authority boundary needs removal from Full access, not a credential bridge.

Avoid exception layering. Each bind, proxy, copied credential and special network route makes a sandbox harder to reason about. When exceptions begin reconstructing the host inside the sandbox, the architecture is telling you that the boundary is wrong.

Distinguish useful sandboxing from sandboxing that defeats product intent. Renderer containment and agent authorization solve different problems. Retaining one does not require lying about the other.

Test the exact user action. A synthetic close event is not necessarily a title-bar X. One dead PID is not a clean application exit. A visible settings card is not functional Computer Use.

Preserve evidence and allow it to reject the result. Exact hashes, real fixtures and fresh review turned “works on my machine” into a bounded, inspectable claim—and caught an incomplete final package before publication.

Finally, simplify as requirements become clearer. The most secure-looking architecture is not automatically the correct one. A boundary earns its place only when it protects something the product is not intentionally authorized to use.
